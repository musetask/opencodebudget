# opencodebudget

给 opencode 的任务时间预算系统。目标不是精确预估，而是**心理预期**：开工前知道大概要多久，执行中偏离能及时发现。重时间，轻费用。

## 核心理念

预估是工作流的副产品，不是独立阶段。

就像妈妈问你几点了：正常情况看一眼表，秒级完成，没人需要预估时间。发现表不走了，你说下楼买电池——心理预期变成 20 分钟。买回来发现还是不走，你说要拿去修，估计 2 小时——妈妈就知道未来 2 小时"时间服务不可用"。

每一次预期都是在分支点上顺手产生的：尝试 → 受挫 → 更新预期 → 换策略。没有"先调研再建模"的仪式，错了就更新，更新成本极低。

## 架构

四层，各干各的：

```
记录层（opencode 插件 event hook，被动）
  │  记账：每一步的 TTFT、解码速度、input/output/cache token、
  │  工具耗时、上下文大小、渠道/模型、机器指纹、任务类型
  │  输出 token 用 max_tokens 封顶；不用 MCP 做记录，
  │  因为 MCP tool 靠模型主动调用，会漏记
  ▼
预算感知（上下文注入，推）
  │  开工时直接注入："本任务预算 30 分钟，历史同类 p50 18 分钟/p90 35 分钟"
  │  偏离时注入提醒："已用 18 分钟，超 p50 了"
  │  模型不调工具也看得到——这是策略选择的前置条件
  ▼
主动查询（budget 工具，拉）
  │  模型按需调用：查某类任务、某个操作的耗时档位
  │  实现就是读 sqlite 的本地脚本，无常驻服务、无 MCP
  │  返回保持紧凑：只给 p50/p90 档位，不倒原始数据烧 token
  ▼
外部中断（hook/插件层看门狗，兜底）
   每步检查偏离，超了直接打断并注入新信息
   只管模型不自觉的时候
```

为什么四层而不是三层：工具的意义不只是查询，是给模型**策略主动性**。同样是修东西，买电池 5 分钟能接受，拆表芯修 40 分钟不能接受——这个判断只能模型自己做，看门狗做不了。外部中断是兜底：30 分钟到了直接停，但这时再选 20 分钟策略的机会已经没了。所以预算信息必须推到模型面前（开工注入、偏离提醒），不能只等它想起来调工具。

## 关键设计决策

1. **只要心理预期**：预估给档位（几分钟 / 一刻钟 / 半小时以上），不给精确数字。人对档位的信任度更高，偏差也被包容。

2. **原子确定，组合分布**：编译 5 万行代码在同一台机器、同一个仓库，耗时长期收敛为常数；不确定的是编译几次、中间插多少步 debug。记录 key 必须包含机器指纹（命令，参数模式，仓库，机器）——多机环境下 key 不带机器，分布就是混在一起的脏数据。

3. **插件是共同记忆**：你和你妈不用约定完成时间，因为你们看的是同一本账。对大模型来说，每个新 session 都是失忆的，插件就是它的账本——plan 和 build 面对同一套历史，口径一致。越用越准不是因为算法好，是因为账本越来越厚。

4. **中断是兜底，不是策略**：每步检查点对比预期，偏离（时间/token 超档位上限）→ 中断当前路径 → 换策略。但外部中断只能管模型不自觉的时候——30 分钟被停时，再选 20 分钟策略的机会已经没了。真正的策略选择必须靠模型自己，这就是预算感知层存在的理由。

5. **推拉结合**：光给工具不够。任务跑飞时模型最可能忘记调工具自查，所以关键信息必须推到上下文里（开工注入、偏离提醒），工具只负责模型主动查细节。推是前置条件，拉是补充。

6. **不做的事**：两次预估仪式、EWMA、肥尾建模等重型统计，常驻计算服务，MCP 查询层。拿精确预估的装备去打心理预期的仗，是过度工程化。工具实现就是读 sqlite 的本地脚本。

## budget 工具提供什么

历史事实查询，例如：

- 20k 上下文在 a 渠道：30 秒
- 50k 上下文在 b 渠道：25 秒
- c 模型遇到计算类问题思考时间过长：超过 50 秒

plan 阶段由插件直接注入粗档位，不用调工具；执行中模型可按需调工具查细节；超过档位上限，触发重估。
