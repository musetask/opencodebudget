# opencodebudget

给 opencode 的任务时间预算系统。目标不是精确预估，而是**心理预期**：开工前知道大概要多久，执行中偏离能及时发现。重时间，轻费用。

## 核心理念

预估是工作流的副产品，不是独立阶段。

就像妈妈问你几点了：正常情况看一眼表，秒级完成，没人需要预估时间。发现表不走了，你说下楼买电池——心理预期变成 20 分钟。买回来发现还是不走，你说要拿去修，估计 2 小时——妈妈就知道未来 2 小时"时间服务不可用"。

每一次预期都是在分支点上顺手产生的：尝试 → 受挫 → 更新预期 → 换策略。没有"先调研再建模"的仪式，错了就更新，更新成本极低。

## 架构

三层，各干各的：

```
记录层（opencode 插件 event hook）
  │  被动记录每一步：TTFT、解码速度、input/output/cache token、
  │  工具耗时、上下文大小、渠道/模型、机器指纹、任务类型
  │  输出 token 用 max_tokens 封顶；不用 MCP 做记录，
  │  因为 MCP tool 靠模型主动调用，会漏记
  ▼
计算服务（本地常驻）
  │  预聚合历史：按（模型，任务类型）维护分布
  │  opencode 在任务时不做计算——花 token 去省 token，本末倒置
  │  对外提供 POST /estimate，返回时间档位，毫秒级
  ▼
查询层（MCP 薄适配器 / 直接 HTTP）
   把计算服务的接口包成 tool，供 plan 阶段调用；
   跨 agent 共享时（比如 pi 也想查）直接调服务即可
```

## 关键设计决策

1. **只要心理预期**：预估给档位（几分钟 / 一刻钟 / 半小时以上），不给精确数字。人对档位的信任度更高，偏差也被包容。

2. **原子确定，组合分布**：编译 5 万行代码在同一台机器、同一个仓库，耗时长期收敛为常数；不确定的是编译几次、中间插多少步 debug。记录 key 必须包含机器指纹（命令，参数模式，仓库，机器）——多机环境下 key 不带机器，分布就是混在一起的脏数据。

3. **插件是共同记忆**：你和你妈不用约定完成时间，因为你们看的是同一本账。对大模型来说，每个新 session 都是失忆的，插件就是它的账本——plan 和 build 面对同一套历史，口径一致。越用越准不是因为算法好，是因为账本越来越厚。

4. **中断机制**：每步检查点对比预期，偏离（时间/token 超档位上限）→ 中断当前路径 → 换策略。超预期的真正含义不是"数字变了"，而是"当前策略不值了"：妈妈让你看着蒸馒头，你花 2 小时去修表，馒头早糊了——应该不修表，直接去邻居问时间。这是计划模板里"止损点"的自动化版。

5. **不做的事**：两次预估仪式、EWMA、肥尾建模等重型统计。拿精确预估的装备去打心理预期的仗，是过度工程化。

## 计算服务提供什么

历史事实查询，例如：

- 20k 上下文在 a 渠道：30 秒
- 50k 上下文在 b 渠道：25 秒
- c 模型遇到计算类问题思考时间过长：超过 50 秒

plan 阶段查一次，给粗档位；执行中超过档位上限，触发重估。
